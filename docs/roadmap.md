# 食刻 · 推进路线

## 产品判断

食刻的核心是：让人看到一种食物就想点开，吃下第一口有反馈，吃完愿意换一种。

定位为手机优先、打开即玩的短时 3D 食物体验。画面让人有食欲，反馈有食材差异，一次体验能自然结束。首轮目标用户是通过分享链接进来的朋友和轻度休闲玩家。

目前已有食物柜 → 进食 → 完成 → 重玩的闭环，只有经典汉堡一种内容。交互框架已经足够支撑下一轮验证；还缺少线上试玩、真实设备反馈和第二种食物的生产验证。

## 推进顺序

### 1. 先交付能分享的试玩版

**产出：一个朋友能直接打开的网址。**

- 部署静态站点，连接 GitHub 自动构建；根据访问地区、HTTPS 与 GLB 加载结果选择托管。
- 构建前检查类型和单测。发布目录只带运行时需要的资源；原始模型留在仓库或资产存储中。
- 当前原始模型也位于 Vite 的 public 目录，构建会一并复制。部署前需排除约 75 MiB 的原件，实际游玩只请求约 10 MiB 的移动版模型。
- 用 iPhone Safari、Android Chrome、桌面浏览器各跑一遍：打开 → 加载 → 吃完 → 重玩，覆盖静音、后台切回与加载失败。
- 找 5 位朋友实际试玩。只收集三个问题：哪里没看懂、哪里不像食物、是否愿意再吃一次。记录设备、首次可操作耗时和明显卡顿。

**完成条件：**无需开发环境即可游玩；目标手机上能完成全过程；没有阻断操作的错误。先测出实际加载耗时，再定优化指标。

### 2. 把汉堡做成内容样板

**产出：一款有食欲、反馈一致的示范食物。**

- 对照真实汉堡照片检查面包烤色、肉饼焦边、蔬菜颜色和咬痕切面；优先修正资产中缺失或错误的纹理与几何。
- 从固定视角核对四阶段对齐、形状与余量变化。淡化能缓和切换，但跨模型的切面连续性仍取决于资产。
- 为汉堡明确材质和光照参数。当前统一校色/粗糙度修正服务于这批汉堡资产，新增食物前应支持按食物配置，避免奶油、糖衣等材质被同样处理。
- 用参考录音或真实设备听感校准音色。单测能验证声音调度，不能证明声音好听。
- 根据试玩反馈决定每阶段口数与节奏；现在的 16 口是原型设置，不作为所有食物的固定规则。

**完成条件：**四阶段没有明显位置跳变、空洞或错误反光；真机声音与画面协调；下一轮试玩中，食物质感和反馈问题明显减少。

### 3. 用第二种食物验证扩展

**产出：两种外观和口感有区别的食物。**

- 建议第二款用蛋糕或其他软质甜点，验证与汉堡不同的颜色、切面和反馈，最终取决于可获得的合格资产。
- 按素材规范提供四阶段 GLB、封面和名称。先验收完整模型及一个咬开阶段，再制作其余阶段，减少返工。
- 接入独立的材质、声音、口数和尺寸校准配置；共享加载、进度和输入逻辑。
- 让封面与实际 3D 食物一致，可从模型固定角度生成封面。

**完成条件：**新增食物不需要修改核心进食流程；手机资源可控；切换食物后，用户能感知它们的差异。

### 4. 再决定持续玩法

前面三步完成后，根据复玩行为决定是否加入食物收藏、轻量完成记录、随机菜单或分享卡。先选择一种能解释用户复玩理由的机制，再做下一轮。

账号、排行榜、付费解锁和后台管理暂不进入当前范围。现阶段先证明食物体验本身能吸引人。
